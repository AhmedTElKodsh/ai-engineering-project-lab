## Acceptance conclusion

**None of D, E, or F satisfies the full updated objective as its current active design.** D is an accelerator for someone with prior AI experience; E is a bounded application-implementer milestone with later specialization options; F is an explicitly unreleased first-milestone pilot. Those are legitimate earlier scopes. Their deliberate exclusions should be described as gaps against the expanded objective, rather than retrospectively treating the exclusions themselves as defects.

The updated endpoint remains one coherent repository and one active learning route: junior basic Python → observable intermediate Python → model APIs, structured output, RAG, tools/agents, state, evaluation, cost and reliability → probability, gradients, backpropagation, tokenization and causal transformers → a complete small language model trained from random weights. Two connected cumulative projects are permissible. Five two-hour sessions each week and CPU-first execution are operating constraints; a GTX 1050 Ti is optional. Learner-owned implementation, adaptive guided examples, fresh transfer, delayed retention, honest state, and a meaningful executable baseline are acceptance requirements.

D contributes compact failure/cost habits and inspectable implementation sources; E contributes a cumulative application spine, scoped primitive exercises, and well-labeled reference verification; F contributes the most explicit extended teaching-depth and evidence-class standards. None should be copied into the resulting repository as an additional active course.

## Project D

### Native design and useful components

Root `README.md:13-15` declares `Layer1-Final/` active, and `Layer1-Final/README.md:4-7` labels it canonical: 28 weeks at **20 hours/week, four hours/day**. Its philosophy explicitly targets building systems with foundation models and a learner with **one year of AI experience** (`:15`). This is an experienced application-engineering accelerator, not a beginner-to-random-weight-model curriculum.

The route has useful engineering continuity: one Git repository, spiral RAG improvements, architecture checkpoints, failure logs, and token/cost tracking (`Layer1-Final/README.md:37-48`). Manual RAG precedes framework rebuilding; a hand-built tool/memory/guardrail agent appears in week 11 (`:92-133`). That preserves inspectable mechanisms before abstractions. The diagnostic has independently written CSV/OOP/REST/typed-filter/test tasks and assigns incomplete work to remediation (`:54-70`). These are useful assessment ingredients, but their breadth and short time box assume more than a junior basic-Python starting point.

The AI-assistant guide supplies conceptual explanation, approach suggestions, analogous pattern examples, debugging, and post-implementation review (`Layer1-Final/guides/GUIDE-FOR-AI-ASSISTANTS.md:26-34`, `:50-152`). It protects learner authorship. Cost-log fields capture date, task, provider/model, input/output tokens, cost, and an optimization decision (`guides/COST-LOG.md:17-43`). Failure-log fields capture symptoms, root cause, repair, time, learning, and prevention (`guides/FAILURE-LOG.md:46-54`). Those compact field sets are more reusable than the many duplicated weekly forms.

Implemented ingestion sources include fixed, recursive, semantic and sentence chunking (`src/ingest/chunkers.py`). This is implementation material, not merely roadmap prose. However, importing the ingestion package also imports loaders, retrieval, metadata and table machinery (`src/ingest/__init__.py:17-75`), which increases the dependency surface for an otherwise small exercise.

### Required fixes and updated-objective gaps

1. **Repair active navigation before using D as a learner entry point.** Root `README.md:13-15` declares Layer1 active, but its linked root `STUDENT-GUIDE.md:24` sends the learner to `Layer2-Curriculum/chapters/phase-0-foundations`, a path absent from the active root. The guide also describes the old phase sequence (`:36-46`). This is a genuine coherence defect independent of the expanded model endpoint. Its “COMPLETE” tables describe lesson/content availability, not proven learner progress; do not import those labels into learner state.
2. **Rewrite pacing and entry assumptions.** Halving four-hour days is insufficient when early weeks contain FastAPI, async CRUD, SQL/migrations, testing, Docker and CI (`Layer1-Final/README.md:76-88`). A junior route needs intermediate-Python gates and small, runnable project changes before that stack. The current 20-hour week and prepared-learner diagnostic do not meet the new 10-hour constraint.
3. **Author the missing mathematical/model-construction route.** The active philosophy focuses on building with models, and the later optional fine-tuning sprint is an application specialization (`:15`, `:112-133`). It does not establish probability, chain rule, manual backpropagation, a tokenizer, causal transformer, output head, training, evaluation and generation from random weights.
4. **Replace rigid help and calendar requirements with adaptive evidence.** “Always start at Level 1” (`GUIDE-FOR-AI-ASSISTANTS.md:50`) and prohibitions on complete solutions (`:36-44`) need an exception for requested worked analogous examples or targeted repairs. The phase checkpoint is primarily verbal recall; borderline results retry in two days (`:547-551`). That delay is useful, but is not an implemented contract for fresh tasks, recorded assistance, changed data/code, and retained independent performance. Weekly pushed commits “No exceptions” (`Layer1-Final/README.md:43`) and mandatory Friday failure entries (`FAILURE-LOG.md:24`) must not encourage invented work or failures.
5. **Do not equate source volume with a verified baseline.** Root README calls `src/` a production FastAPI application (`README.md:27`), but an end-to-end service entry point was not established in the inspected active startup surfaces. The selected offline test could not collect because `tests/conftest.py:4` requires an unavailable dependency. This is an environment limitation, not proof that the chunker implementation is wrong. The broad root `requirements.txt:1-52` should not become the beginner dependency set.

The progress tracker is an honest blank template: learner fields are blank and all initial phases are not started (`Layer1-Final/guides/PROGRESS-TRACKER.md:3-19`). Its checkboxes and scores are not a resumable event ledger, freshness resolver, or independent-transfer proof. An aggregate `guides/results.json` does not establish a learner's competence or provenance.

**Reuse:** compact failure/cost field sets, selected small algorithms after isolation and focused verification, the analogy/pattern-example ladder, and mechanism-first RAG/agent cases. **Archive rather than activate:** the conflicting root student guide, old layers, the 28-week calendar, duplicated weekly forms, broad framework rebuild tours, and advanced infrastructure tracks. Retain their original scope as history.

## Project E

### Native design and useful components

E explicitly targets learners with working Python fundamentals and a bounded **M1 AI Application Implementer** route: 30-hour fast path, 40-hour full path, plus five recovery hours (`README.md:3-10`; `START_HERE.md:47-56`). It distinguishes that milestone from independent production ownership and later specialization (`START_HERE.md:9-19`; `curriculum/main-track/milestones.md:9-11`). It does not claim advanced mastery from the short launchpad.

The active route builds one cumulative FinAgent application: deterministic baseline → model boundary and evaluation → RAG → bounded tool workflow → service/operations → transfer defense (`START_HERE.md:58-75`). The root principles are learner-owned code, inspect/predict/run/implement/verify/explain/transfer, evaluation before probabilistic behavior, evidence before tools, and workflows before autonomy (`README.md:74-84`). `START_HERE_2_HOURS_PER_DAY.md:3-6`, `:21-31` provides twenty two-hour sessions, with constrained recovery. The map treats timing as a design budget, records overruns, and requires continued work when exit evidence remains unmet (`curriculum/main-track/milestone-1-45-hour-map.md:3-14`, `:57-68`).

The cumulative workbench explicitly separates expected TODO failure from collection/setup failure and states that its full test suite is not transfer certification (`curriculum/main-track/06-capstone-projects/week-03-integration-build/README.md:32-50`). Its unfamiliar change requires an owned failing test rather than copying a reference (`:94-104`), and its defense calls for the learner's code, tests and failure explanations (`:108-119`). Bounded support-lab detours return to the cumulative app (`:54-73`). These are good antidotes to disconnected exercise accumulation.

E also has useful plain-Python primitive contracts. The byte-pair tokenizer uses a byte vocabulary, merges and Unicode round-trip behavior (`curriculum/main-track/02-module-2-first-principles/week-01-tokenization/README.md:37-41`; `tests/test_tiny_tokenizer.py:48-93`). Optional internals cover stable softmax, vector/matrix projection, attention, residuals, normalization and a traced forward block (`curriculum/extended-concepts/01-model-internals/week-01-tiny-transformer/workbench.py:25-101`). A separate linear-gradient exercise clarifies training versus inference and adaptation choices (`week-02-training-vs-inference/README.md:32-36`, `:53-54`).

### Required fixes and updated-objective gaps

1. **Extend rather than mislabel the endpoint.** M1 deliberately defers BPE/attention/training (`START_HERE.md:101-111`). The forward-block lab expressly says it is not training (`curriculum/extended-concepts/01-model-internals/week-01-tiny-transformer/README.md:45`). Its scaffold implements attention over the sequence and a single projected feed-forward step; it specifies neither a causal mask nor a complete language-model output/training path (`workbench.py:78-101`). Linear-gradient updates are not backpropagation through a transformer. These are good prerequisites; a complete random-weight causal LM still must be designed and implemented.
2. **Define intermediate Python competence and include remediation in total planning.** The five-test placement sample checks swap, flatten, closure, counter and divide-by-zero cases (`START_HERE.md:23-39`). Working Python and remediation outside the M1 clock are explicit. Under the new beginner-to-intermediate objective, modules, data modeling, iterators, exceptions, serialization, testing, and independent changes need observable gates. Do not retain the 30–45-hour M1 total as the total expanded course estimate.
3. **Resolve supporting-document sequence drift.** The active start page defers model internals, while `curriculum/main-track/02-module-2-first-principles/AI_AUTHORING_GUIDE.md:7` still says learners build tokenization/embedding/attention before LLM APIs. Its `:16`, `:36` excludes full model training from M1. The active root authority is clear, but supporting author guidance must be updated when the new route promotes selected primitives to required milestones.
4. **Add durable progress and delayed-retention machinery.** Evidence notes, AI-help disclosure, unfamiliar changes and defense are strong (`HOW_TO_USE_AI_ASSISTANTS.md:6-19`, `:30-35`; cumulative README above). No centralized current route/state resolver or required delayed-retention event was established. A completion note or successful instructor reference run must not become a learner's completion event.
5. **Keep maintainer reference readiness distinct from learner ownership.** `LEARNER_READY_MATRIX.md:8-15`, `:50-64` and `README.md:90-107` already distinguish documentation health, scaffold readiness, reference proof, live proof and mastery. Preserve that distinction when making the useful reference available after a serious attempt. The learner workbench remains TODO, even though the completed maintainer reference runs.

**Reuse:** the single cumulative spine, support-lab return rules, focused TODO contracts, unfamiliar-change defense, byte-level tokenizer tests, stable numerical primitive exercises, and the optional completed fixture-backed CLI/HTTP reference. **Archive rather than activate:** older module sequences, M2/M3 as independent competing curricula, broad optional shelves and old assumptions that M1 excludes the newly required model endpoint. The selected primitive exercises should be rewritten into the one active route.

## Consolidation acceptance conditions

These conditions follow from the common objective and the independent findings; they do not select an overall winning original repository.

1. Establish one route, one next-checkpoint resolver and one tutor authority. Active root guides, per-project contracts, event-derived learner state and installed skill must agree. Preserve histories and supplementary support notes separately from active completion claims.
2. Define observable intermediate-Python competence before escalating stack complexity. Teach through the cumulative application's data, modules, contracts, iteration, errors, serialization and tests. Treat focused repair as part of actual learning time rather than concealing it outside a headline budget.
3. Maintain a useful offline baseline and fixtures. Mark inherited/reference/support/learner-owned proof separately. An expected TODO failure can be a good exercise but cannot substitute for the repository's promised runnable baseline.
4. Make common applied capabilities required, cumulative and bounded: a real API boundary with optional live access, structured output, source-grounded RAG, typed tools, workflow/agent state, evaluation, latency/cost, retries and failure handling. Adopt a framework only after its mechanism and tradeoff are understood.
5. Define the model endpoint precisely: random initialization, owned tokenizer/data pipeline, causal masking, complete forward path and next-token head, loss, gradients/backpropagation, parameter updates, checkpoint/reload, generation and held-out evaluation. CPU smoke/learning/training profiles need measured runtime and memory limits. A linear-gradient demo or untrained forward block is a prerequisite, not the endpoint.
6. Connect the model project through data provenance, splits, contracts or evaluation without promising that a tiny educational LM will outperform the support application's baseline or provide production-quality answers. Keep bounded SFT/LoRA literacy optional after the random-weight endpoint.
7. Use requested worked analogous examples, progressive traces, focused hints and repairs. Record assistance honestly, then assess fresh transfer and delayed independent retention. Readiness, completion, runtime proof, live proof and retained independence must remain distinct.
8. Plan five two-hour sessions per week, with visible setup/debug/recovery time and evidence-based advancement. Original 28-week/20-hour, 30–45-hour M1 and 33-hour pilot budgets describe prior scopes; they are not evidence for the complete new path.

The useful consolidation is a selected set of mechanisms and contracts, not six active route trees or six progress systems. Content that fails the active-route criterion can remain valuable reference material without appearing in the learner's next-step surface.
