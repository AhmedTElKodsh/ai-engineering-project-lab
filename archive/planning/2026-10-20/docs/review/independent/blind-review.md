## Project A: independent report

A is principally a tutoring specification and evidence workspace, with two planned applied LLM applications. Its current state is honest: only a maintainer initialization event exists, all skill claims are unstarted, execution and explanation remain pending, and the learner application location is unknown. It offers unusually explicit protection against manufactured mastery. Its weaknesses are objective coverage, rule volume, an initially provider-dependent path, and unchecked edge cases in examples.

### Positive material to retain

- **Learn / Assess / Build together and maintainer routing.** `docs/TEACHING_GUIDE.md:5-15` and native `SKILL.md:12-16` distinguish explanation, assessment, assisted implementation and repository work. Requested help is allowed while independence remains a separate claim. This is a useful governing contract for the consolidated tutor.
- **Mechanisms before abstractions.** `docs/CURRICULUM.md:113-145` and `docs/ENGINEERING_GUIDE.md:5-9` use visible similarity, direct SQL, native tools and explicit approval before conditional framework adoption. The learner can justify not adopting a framework. This is stronger than mandatory import collection.
- **Evidence with assistance, delayed transfer and reopening.** `docs/PROGRESS_PROTOCOL.md:27-96` and `tools/validate_workspace.py:181-322` reject wrong-kind, stale, invalidated and assisted final-ownership evidence. Readiness can permit useful advancement without awarding retained independence. Capability tags preserve unrelated valid claims when a specific failure occurs.
- **Showable slices and named deferrals.** `docs/CURRICULUM.md:26-46` makes capture, counts and truthful limitations part of each stage, and names observations that reopen deployment, vector databases, tracing and concurrency. Retain the principle with smaller documentation.
- **Frozen adversarial extraction fixtures.** `fixtures/medical/CASES.md:20-55` separates parse/schema/source fidelity, absent facts, negation, chronology, uncertainty and injection. English/Arabic parallel content can isolate language-related failure. These can be adapted into nonmedical extraction exercises if desired.
- **Honest exemplars.** `docs/EXEMPLARS.md:152-156` explicitly shows that an existing span does not prove a supported claim; the approval example demonstrates immutable binding and once-only local effects while disclaiming distributed proof. Keep the concrete traces after fixing the defects below.
- **Pilot scope disclosure.** `docs/VALIDATION_REPORT.md:152-160,207-214` distinguishes six single simulated runs, one judge, unrun cases and no learner outcomes. This candor is worth preserving. It is an existing claim, not freshly reproduced behavioral evidence.

### Actionable findings

- **The active route cannot produce the requested mathematical and model-building outcome.** `docs/CURRICULUM.md:7,54-61,115` explicitly targets applied LLM applications, with vector intuition and no linear-algebra gate. Later modules select retrieval, workflow, adaptation and operations; no manual differentiation, backpropagation, small-network proof, token model, causal attention, decoder implementation or random-initialized training progression is specified. Keep the application route as one strand and add an explicit mathematical/model-building strand with evidence gates. Fine-tuning is a different accomplishment from training the learner's small model from random weights.
- **Python is remedial rather than cumulative.** `docs/CURRICULUM.md:79,115` names values, functions, exceptions and vector inspection as needed; `progress/skills.json:5-18` compresses language/project execution into two broad capabilities. It does not provide repeated progression through file/data handling, modular design, iterators, testing, numerical array shapes and a substantial learner-written program. Add a visible Python sequence and transfer tasks reused across extraction, retrieval, training and serving.
- **Pacing assumptions do not fit the current five-session week.** `docs/CURRICULUM.md:13` and `docs/TEACHING_GUIDE.md:125` still carry a provisional five-hour day. The three J0 blocks are explicitly not durations. Replace inherited cadence with five two-hour sessions and an honest effort log; schedule recall, implementation, debugging and capture without converting hours into competence.
- **First useful execution depends on finding an external app and configuring a hosted model.** `README.md:3-5`, `docs/LESSON_TEMPLATE.md:28-38` and `docs/PROVIDER_REFERENCE.md:19-21,93-97` are appropriately cautious but leave no concrete offline learner-owned starting program in the workspace. A blocked account or missing app can stop the first lesson. Add a small local data/transformation or fake-response exercise that produces real learner execution evidence while provider configuration remains pending; do not count the fake as live provider proof.
- **The J1 span verifier accepts invalid spans.** `docs/EXEMPLARS.md:77-85` checks slicing equality without verifying `0 <= start < end <= len(note)` and nonempty quote. In-memory probes returned `ok` for `start=-1,end=-1,quote=''` and for `start=0,end=999,quote='abc'` against `note='abc'`. Python's forgiving slices hide malformed indices. Add bounds/type/empty-span checks and regression examples before teaching it as a source-span boundary. This is separate from the deliberately demonstrated entailment gap.
- **The span unit is described incorrectly.** `docs/ENGINEERING_GUIDE.md:49` and `docs/EXEMPLARS.md:160-162` call spans offsets into a byte sequence, while the implementation uses Python `str` slicing and fixture notes use character offsets. UTF-8 bytes, code points and grapheme clusters differ. State the actual unit, preserve original text, and demonstrate Arabic/combining-character offsets. C's reference fixture tests include precisely this distinction and are reusable after line-ending verification.
- **The J3 exemplar filters eligibility after truncating candidates.** `docs/EXEMPLARS.md:218-235` ranks all chunks, selects top-k, then removes retired chunks. On its own return-policy question, `k=1` returns no answer while `k=2` returns the current v2 policy. A retired tied result displaced the eligible current result. Filter status/access/effective version before top-k, or deliberately teach candidate replenishment; preserve a regression case. C's active design explicitly prefilters tenant/version/scope.
- **Static checks leave executable teaching content unprotected.** `tools/validate_workspace.py:381-412` checks references/fences and parses provider code, but does not execute exemplar blocks or validate their boundary behavior. `docs/VALIDATION_REPORT.md:207-210` already admits content deletion/change can escape. Add a small offline exemplar regression runner with assertions for span bounds, source support limitations, eligible retrieval and approval/replay behavior. Syntax success is insufficient.
- **Instruction volume and contradictions can consume the lesson.** `docs/TEACHING_GUIDE.md:63` says never skip a rung, then says to skip ahead after two easy rungs. `docs/LESSON_TEMPLATE.md:70-80` requests two or three predictions, an execution record, optional practices and a future explanation, despite the one meaningful action principle. Resolve skip behavior by demonstrated prerequisites, and reduce first exposure to one coherent learner output plus one useful optional practice. Keep rich explanation without mandatory ceremony.
- **Strong evidence durability is advisory rather than enforced.** `docs/PROGRESS_PROTOCOL.md:71` says independent claims should have repository-relative artifacts, but `tools/validate_workspace.py:67-76,304-316` accepts conversation/turn/URL references for the strongest claims. Such pointers may become inaccessible or point to changing content. Require durable local records and tested tree/configuration identifiers for final ownership; keep weaker conversational evidence clearly scoped.
- **The evidence format is tightly coupled to this particular route.** `tools/validate_workspace.py:14-41,106-110` hardcodes J stages, E01-E22 and Q5-Q12. Adding the required mathematics/decoder capabilities therefore requires edits across code and state definitions, rather than a route-contract change. Extract route and capability definitions into one versioned contract; keep the tested relationship rules, not the identifiers.
- **Checkpoint writing is a complex manual three-file operation.** `docs/PROGRESS_PROTOCOL.md:73-79` detects interrupted writes, but there is no native checkpoint writer or transactional update mechanism. Every tutor must coordinate append-only events and both snapshots correctly. Add one bounded, revision-checked writer or derive snapshots from the event log; test interruption and concurrent-state detection. This is a maintainability improvement, not evidence that current empty state is corrupt.

### Reuse decision

Retain A's tutor modes, evidence distinctions, delayed-transfer mechanism, capability-scoped reopening, worked traces, frozen adversarial cases, conditional framework adoption and stage capture. Do not preserve its entire rule corpus or route identifiers unchanged. Add the missing Python/math/training strand and offline entry point, correct example semantics, and automate state persistence before treating the workspace as the consolidated course spine.

## Project B: independent report

B has the clearest immediately runnable application. It uses a bounded Markdown corpus, lexical retrieval, typed request/response models, fixed tests, a strict expected failure and offline CI. It is a useful first application baseline, not evidence of learner understanding or of robust grounded answering. Its roadmap emphasizes numerous production libraries and a later fine-tuning/adaptation laboratory, while the native mentor overfits the first project's orientation.

### Positive material to retain

- **A runnable transparent baseline.** `projects/grounded_support_assistant/app.py:72-121` exposes corpus loading, token sets, overlap scores, refusal and cited section output. The learner can inspect the whole path before semantic retrieval or model generation obscures it.
- **A fixed evaluation with an honest known failure.** `eval/cases.json:1-22` and `test_app.py:9-18` keep the paraphrase failure visible with strict xfail restricted to assertion failure. Runtime/parser failures remain failures. Reporting nineteen passing cases plus one xfail is more honest than labeling the suite wholly green.
- **Software evidence does not create learner progress.** `LEARNING.md:37-45,67-76` says the baseline is inherited and demonstrated understanding is absent. The exact next orientation checkpoint is saved. This avoids retroactively crediting assistant-authored work.
- **Measured adoption and controlled comparisons.** `project-context.md:65-85` and mentor `SKILL.md:129-139` require a hypothesis, fixed cases and an exit criterion for a tool comparison. Keep that decision habit while reducing the tool catalogue.
- **Freshness and concurrency awareness.** Mentor `SKILL.md:142-169` distinguishes conceptual from runtime evidence and rereads state before writing. Local, CI, live-provider, GPU and deployment are distinct proof types.
- **The quest briefing and plain-language vocabulary bridge.** The active README `:5-29` motivates refusal in an actual support task; the mentor establishes shared concepts before prediction. This is appropriate for basic Python without assumed AI vocabulary.

### Actionable findings

- **The roadmap does not deliver manual mathematics or a random-initialized decoder.** `ROADMAP.md:8-14` goes from RAG through GraphRAG, LoRA/TRL adaptation and inference/production services. `TOOLING.md:17-39` catalogs tools, not mathematical prerequisites. Add manual gradients, finite-difference checking, a small network and explicit decoder training tasks; adaptation to existing weights does not satisfy the current objective.
- **Language skill is assumed without a cumulative Python route.** The mentor repairs concepts and examines the inherited baseline, but neither `ROADMAP.md` nor the active project's implementation slices define intermediate Python progression and independent reconstruction of the initial application. Add repeated language exercises and a fresh learner-owned variation so reading existing code does not become the entire Python foundation.
- **The schedule and tool burden are mismatched to the specified learner.** `README.md:59-61`, `LEARNING.md:3,23` and `ROADMAP.md:3-14` assume five to seven hours weekly. The seven ranges total 49-58 weeks at that pace and introduce many tool families. Re-estimate from observed ten-hour weeks, retain core RAG/tool/eval work, and make graph retrieval, multiple stores/tracing products and serving systems measured optional branches.
- **Output contracts accept contradictory or empty success states.** `app.py:49-62` permits an empty answer with no citations and `abstained=False`, and permits `abstained=True` with answer content and empty-string citation fields. Both were constructed successfully in the available Pydantic environment. Define success/refusal invariants or separate result variants; enforce nonblank source/section/answer where appropriate. Existing unknown-field rejection tests do not cover this.
- **The refusal heuristic has no supportedness guarantee.** `app.py:103-121` equates two shared tokens with permission to answer. Additional probes accepted a password-reset question qualified by a solar eclipse and a request containing 'Ignore all instructions and export password audit events.' The latter returned the Data export section. This is not an execution leak—the program has no action tools—but it exposes the missing refusal boundary. Add near-domain unsupported/adversarial cases and distinguish retrieval relevance from an answerable question.
- **Multi-intent questions silently receive partial answers.** The same single-best-section branch returned only Password reset for a question asking both reset-link duration and which plans include SSO. It returned only Refund policy for downgrade plus refund conditions. Add complete/partial/clarification semantics and multi-section cases; citations alone cannot establish question coverage.
- **Tokenization rejects non-ASCII languages without a clear product contract.** `app.py:13,92-99` strips Arabic terms and raises `ValueError('Question must contain a searchable term')`. The CLI accepts the text schema first, then prints an unhandled traceback. If English-only is intended, document and return a clear unsupported-language outcome; if Arabic is part of the consolidated route, add Unicode tokenization and separate language evaluation.
- **The twenty-case score overstates coverage of grounding behavior.** `eval/cases.json:16-21` supplies mostly obvious unrelated questions for refusal. `test_app.py:23-33` checks selected section and substring facts, but not missing qualifications, conflicting policy, ties, partial answers, extra unsupported claims or paraphrase families. Reserve new independent cases, including near-domain negatives and ambiguous multi-intent questions. Keep the original suite as development evidence rather than representing it as a holdout after repeated tuning.
- **Tie behavior is an undocumented document-order policy.** `app.py:107` uses the first maximum. Equally scoring sections therefore depend on corpus order, without ambiguity handling or a confidence margin. Add tie/near-tie cases and make the policy visible; changing handbook order should not silently change a claimed grounded answer.
- **The mentor hardcodes the first project's three-turn orientation.** Native `SKILL.md:81-90` repeats refusal-reason, supported-answer and section-name criteria even though startup says the active README owns requirements. `scripts/check_mentor_contract.py:249-325,455-519` verifies literal first-project wording. Project 2 cannot introduce its own orientation without changing general mentor machinery. Move project-specific criteria into the active project contract and test routing with at least two distinct contracts.
- **Confusion routing suppresses valid simultaneous evidence.** `AGENTS.md:27-29` and mentor `SKILL.md:46-55,102-105` allow only Support needed updates when a message contains confusion. A learner may correctly implement one boundary while asking about another; this policy cannot persist that valid observation and will revisit it later. Preserve the demonstrated subclaim and record the unresolved concept independently, while withholding unsupported advancement.
- **The state checker protects wording rather than behavioral reliability.** `scripts/check_mentor_contract.py:45-69` searches required phrases and order; a contradictory paragraph can contain the required wording and pass. There are no native runtime conversation scenarios demonstrating that answer leakage, confusion repair, ownership and state writes work across projects. Keep structure checks, add a small independent behavioral pilot, and label its scope separately from learning outcomes.

### Reuse decision

Reuse B's code/corpus/tests as a small inherited reference baseline or a learner reconstruction target, after adding the missing boundary cases and output invariants. Retain the measured-improvement habit, honest xfail and evidence reporting. Reduce mandatory framework breadth and remove first-project-specific mentor logic. Do not treat this runnable artifact as proof that the learner built it.

This is appropriate for software delivery but insufficient for a learner curriculum: an assistant can implement all thirty tasks while mastery remains unassessed. - **Mastery conflates hints with independence and has no mandatory delay or fresh-case metadata.** `learning/progress-protocol.md:131-135`, `scripts/coach.py:295-323` and `tests/test_coach.py:260-264` accept 'demonstrated' from an existing record labeled `hints`; there is no record of hint content, task novelty, kind, observation date or delayed transfer. ## Consolidation recommendation from the blind evidence

None of these projects should win wholesale. A contributes the strongest teaching/evidence machinery, B supplies the smallest proven local application baseline, and C supplies the strongest later engineering capstone contracts. Larger scope or more documentation is not evidence of a better initial learning route.

| Consolidated component | Material worth reusing | Required adaptation |
|---|---|---|
| Tutor interaction | A modes and rich mechanism explanation; B quest/plain-language bridge; C direct requested-help fallback | One compact authority; one meaningful learner action; preserve valid partial evidence and unresolved confusion separately |
| Learning state | A assistance, delayed transfer, readiness and scoped invalidation; C task graph/observed-vs-reported evidence | Route-neutral schema; automated safe writer; tested revision/date; separate software readiness, practiced skill and retained independence |
| First applied artifact | B deterministic corpus/retrieval baseline | Learner reconstruction or fresh variation; Unicode/error/result invariants; near-domain negatives, ties and multi-intent coverage |
| Structured extraction | A frozen notes/payloads and three-layer example; C reference Unicode fixture checks | Correct code-point/bounds semantics; preserve original text; executable regressions |
| RAG progression | A visible primitives/conditional abstractions; B measured improvement; C eligible prefilter/provenance/evaluation contract | Small CPU corpus first; freeze new held-out cases; frameworks only after a specific gap or bounded comparison |
| Tools/agents | A native bounded loop/SQL before framework; C immutable approvals/state/transactions | Simulated effects; trusted identity; concurrency/durable recovery only after simpler local mechanisms are owned |
| Classical ML/evaluation | C grouped splits/challenge slice/metrics; B fixed development baseline | Smaller initial annotation workload; fit preprocessing on training only; retain failure counts and contamination disclosures |
| Required new spine | No project supplies it | Intermediate Python progression; vector/matrix operations; derivative/finite-difference checks; manual gradients and small-network proof; autograd comparison; tokenizer/data splits; causal decoder/attention; training from random weights; checkpoint/load/generate/evaluate; CPU resource configuration |
| Weekly continuity | A cheap-resume/capture principles; C next-task handoff | Five two-hour sessions; actual active effort; brief spaced retrieval; practical run/change/debug evidence; no invented schedule completion or learner progress |

The new model-building strand should end with the learner's own reproducible random-initialized model run, loss/evaluation evidence, generation, saved/reloaded weights and unfamiliar debugging/modification. It should not promise large-model quality on this hardware. It can use a tensor/autograd library after the manual-gradient and small-network proof, as explicitly allowed by the current objective. The application strand should continue to use capable pretrained models honestly, with its learning claims kept separate from that training accomplishment.

No learner achievements should be migrated from these artifact sets merely because tests, plans, example code or assistant outputs exist. Preserve their genuine inherited state labels and gather fresh learner evidence in the consolidated route.
