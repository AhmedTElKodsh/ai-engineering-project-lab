# Blind acceptance and educational-design audit

Audit date: 2026-10-11. Inputs were only `blind/project_A`, `blind/project_B`, and `blind/project_C`. I did not inspect original checkouts, identity mapping, backups, prior discussion, or other review reports. Each design was first evaluated on its own native authorities, then against the same updated objective. Vendor breadth was not scored. Snapshot contents were read only; checks were offline, with bytecode and pytest cache writes disabled. No dependency install, provider call, or external service was used.

Evidence paths below are relative to `D:/AI Projects/Learning/.consolidation-2026-10-11/blind/`. Textual line references use `rg -n` numbering (LF-delimited source lines). Some B/C snapshot files contain repeated CR characters, so Python tracebacks and PowerShell text readers can display different line numbers; traceback numbers are identified separately when quoted.

## Acceptance conclusion

**None of the three original designs fully satisfies the updated objective without substantial route changes.** This is a scope comparison, not a claim that each design failed its earlier intended purpose. A explicitly targets applied LLM application roles; B separates portfolio practice from a from-scratch curriculum; C explicitly excludes foundation-model pretraining. Those prior boundaries explain the common missing endpoint.

The strongest reusable combination is **A's evidence/retention kernel and adaptive teaching depth, B's executable transparent baseline and quest-first onboarding, and C's requirement-to-task traceability and bounded operational failure cases**. Keep one active route and one tutor in the resulting repository. Copying all three routes or progress systems would fail the coherence requirement.

The acceptance endpoint must include an explicit basic-to-intermediate Python bridge, the applied AI mechanisms, a mathematical/model-construction sequence, and a complete small causal language model trained from random weights. An optional LoRA exercise, a classical classifier, or running a pretrained model cannot substitute for that endpoint.

## Project A: independent assessment

### Native scope and strengths

A openly identifies itself as curriculum and portable evidence rather than an observed application (`project_A/README.md:3-5`; `AGENTS.md:3-5`). Its authoritative route is J0–J5, with synthetic medical extraction transferring into retail classification, retrieval, order tools, and approval. The two products have different users and engineering responsibilities (`docs/CURRICULUM.md:15-24`); the route connects them through structured-output and domain-transfer work (`:54-61`, `:101-109`). This is a valid two-product learning design under the earlier applied scope.

It supplies the most developed evidence discipline. The protocol separates execution, explanation, modification, debugging, and delayed transfer; records assistance; treats generated work as support; and preserves corrections in an append-only log (`docs/PROGRESS_PROTOCOL.md:27-51`, `:53-71`). Independent claims require multiple evidence kinds and delayed transfer. Readiness can permit productive advancement while retention remains pending, and later contradictory evidence reopens only affected capabilities (`:88-103`). This avoids making a review date an artificial barrier to useful work.

Teaching includes decomposition of dense expressions, representative traces, complexity rungs, adaptive help, direct answers, and re-entry after a gap (`docs/TEACHING_GUIDE.md:17-25`, `:57-75`, `:127-137`; `.agents/skills/ai-engineering-tutor/SKILL.md:34-46`). Local schema/source/authorization checks arrive with the relevant mechanism; full deployment/test infrastructure is deferred with explicit reopening triggers (`docs/CURRICULUM.md:26-44`). Approval binds trusted actor, target, exact parameters, and proposal identity; mutation and replay must produce zero effects (`:130-145`). These are concrete engineering ideas, not a framework checklist.

The current log contains only a maintainer initialization, explicitly asserting no learner competence (`progress/evidence.jsonl:1`). App path and installed versions are unknown and the first-call execution/explanation gates remain pending (`progress/current.json:16-53`). All initial skill rows are `not_started` (`progress/skills.json:5-176`). This is honest continuity rather than fabricated progress.

### Gaps against the updated objective

1. **The route stops at applied delivery, not model construction.** The mission says this is not a general ML research curriculum (`docs/CURRICULUM.md:7`). Later Q10 offers local inference and optional LoRA/QLoRA with minimal tensor/training concepts as needed (`:169-184`). There is no mandatory probability → gradient → backprop → tokenizer → causal transformer → random-initialized training chain. Preserve the original scope statement as history and replace the active endpoint.
2. **Basic/intermediate Python remains incidental.** J0 supplies values, containers, functions, exceptions, modules, tracebacks and Git as needed (`:79`), and J3 requires enough Python to inspect lists, vectors and functions (`:115`). This does not define or assess intermediate Python competence across modules, data modeling, iterators, errors, serialization, testing, and an independently modified application.
3. **No runnable application baseline exists in the snapshot.** The explicit unverified external app location is sensible prior continuity, but a new single repository needs a useful offline baseline under its own project directory. Medical fixture notes and malformed outputs help validate a later implementation; they are not that implementation.
4. **Pacing conflicts with the new fixed constraint.** The inherited five-hour study day is provisional (`:13`; `docs/TEACHING_GUIDE.md:125`), and J0 block size explicitly claims no session duration (`docs/CURRICULUM.md:69`). Rewrite pacing to 10 hours weekly, five two-hour sessions, preserving measured setup/learning time and evidence-based progression.
5. **The initial state is historical continuity, not new diagnostic proof.** `complete_inherited` onboarding and provider selection are traceable but should not become certification in a merged route. Migrate them as inherited context, with the null app/environment fields retained until inspected.

### Reuse and archive decision

Reuse the append-only evidence model, correction/freshness rules, conservative initial skill state, requested assistance modes, annotated exemplars, source-span fixtures, approval mutation/replay cases, and deferral triggers. Simplify maintenance-only machinery presented to the learner. Retain the frozen V3.2 pack as historical/reference material, as A already instructs (`README.md:32`; `AGENTS.md:9`). Do not activate both frozen and native routes, or the J/Q labels as an additional competing route.

## Project B: independent assessment

### Native scope and strengths

B has the strongest immediately reviewable product start. Its inherited Grounded Support Assistant uses a bounded Markdown handbook, strict Pydantic boundaries, deterministic token-overlap retrieval, citations, abstention, and twenty evaluation cases. The paraphrase limitation is a declared strict expected failure, rather than hidden as success (`README.md:10-20`; `projects/grounded_support_assistant/README.md:22-39`; `project-context.md:87-113`).

The quest clearly names the learner's role, users, failure cost, and inherited prototype before introducing AI vocabulary (`projects/grounded_support_assistant/README.md:5-29`). Mentor startup validates local authority and the active project; it refuses to treat inherited code as knowledge (`.agents/skills/project-mentor/SKILL.md:18-41`, `:56-91`). The baseline is an artifact to investigate, not a claim that the learner authored it.

The state explicitly records no demonstrated understanding, an uncompleted quest briefing, and old runtime/CI proof separate from learner comprehension (`LEARNING.md:32-52`, `:66-75`). Project-wide authority is explicit: current learning evidence, per-project contracts, sequence, and tool-adoption rules have distinct owners (`project-context.md:123-130`). Fresh runtime proof is required for implementation checkpoints, whereas conceptual checkpoints need learner explanation, not invented commands (`.agents/skills/project-mentor/SKILL.md:140-173`).

### Gaps against the updated objective

1. **Seven cases and a separate from-scratch track do not satisfy one connected route.** The roadmap deliberately chooses seven recurring project cases (`ROADMAP.md:3-14`). `LEARNING.md:57` carries the decision to keep the portfolio lab separate from the from-scratch curriculum. This was a reasonable prior portfolio choice but directly conflicts with the new consolidation objective. Fold useful capabilities into one cumulative application and one connected small-model project; archive independent cases as extension ideas.
2. **Adaptation is not training from random weights.** The model case lists datasets, pretrained-model tooling, PEFT/LoRA, TRL and experiment tracking (`ROADMAP.md:12`). Neither that row nor the active project slices specify mathematical primitives, manual backprop, tokenization, causal attention or a complete small model trained from scratch. The endpoint must be authored, not assumed from the word “training.”
3. **Python progression is not explicit.** The existing implementation includes dataclasses, typed models, parsing, functions and CLI arguments (`projects/grounded_support_assistant/app.py:43-80` and later functions), but no learner-owned prerequisite bridge or intermediate Python gate connects them to future training code.
4. **Retention is weaker than the other designs.** Check-understanding supports retrieval/transfer and project mastery includes an independent change, but there is no delayed-retention event or freshness contract (`ROADMAP.md:16-25`; mentor `SKILL.md:65-66`, `:147-159`). The instruction to display all project facts and never test recall of a previous turn (`:95-100`) is appropriate for source comprehension but should not govern a separate voluntary retention exercise. Keep grounding checks distinct from retrieval of previously demonstrated mechanisms.
5. **Orientation and confusion rules can become unnecessarily rigid.** Three orientation criteria must occur in separate turns (`projects/grounded_support_assistant/README.md:46-57`), and mixed confusion permits only support-state updates even if other evidence is valid (mentor `SKILL.md:46-55`, `:102-105`). Keep the principle that unfamiliar vocabulary is explained first; allow sufficiently clear actual evidence to satisfy multiple appropriate criteria, and distinguish a request for explanation from a demonstrated failure.
6. **Pace and hardware contract are missing.** `ROADMAP.md:3-4` and `LEARNING.md:3` assume 5–7 weekly hours. GPU-heavy tooling is conditional in the serving case, but no CPU-first training budget or GTX 1050 Ti optional path exists. Tool comparisons should be bounded electives once a concrete gap is visible, not all mandatory steps before the model endpoint.

### Reuse and archive decision

Reuse the original local handbook, lexical baseline, fixed evaluation, strict expected-failure convention, factual answer assertions, clear quest framing, learner-owned post-baseline slices, and observed-proof labels. Adapt dependency boundaries to the resulting repository's declared policy. Archive the seven-case tool catalogue, serving and GraphRAG branches, and deployment-heavy capstone as optional extensions. Do not carry the “separate from-scratch curriculum” decision into active authority.

## Project C: independent assessment

### Native scope and strengths

C is the strongest detailed application plan. It defines one sandbox commerce workflow with server-owned identity, tenant-scoped reads, case/order binding, deterministic eligibility, immutable approval, execution-time revalidation, and duplicate prevention (`projects/commerce-support-copilot/AGENTS.md:35-36`; `docs/00-project-brief.md:7-11`, `:41-43`). It explicitly distinguishes the coach from the runtime copilot and distinguishes synthetic results from real business benefit.

Thirty tasks have direct dependencies, requirement IDs, planned files, focused tests, acceptance behaviors and teach-backs (`docs/09-backlog.md:3-42`). Release levels permit a read-only demo before later operations (`docs/08-roadmap.md:16-36`). The helper validates dependency order and recommendations without pretending to run product tests. The current task is null, all tasks are `not_started`, and mastery is `unassessed` (`learning/progress.json:1-14` and repeated rows).

Its evidence protocol distinguishes software completion from understanding, requires test plus review artifacts for `done`, preserves old evidence when reopening, and labels observed versus learner-reported evidence (`learning/progress-protocol.md:30-56`). Coaching offers prediction, hypotheses, retrieval warm-ups, autopsies, and requested worked examples without converting those offers into gates (`skills/commerce-ai-coach/SKILL.md:52-58`; `references/coaching-playbook.md:35-60`). The application evaluation plan separates twelve development seeds from a much larger intended locked evaluation, and calls the latter a requirement rather than a result (`docs/06-evaluation-and-testing.md:12-30`). Classical ML includes grouped partitions and a separate handwritten challenge slice, a useful anti-leakage practice (`docs/05-ai-and-rag-design.md:56-64`).

### Gaps against the updated objective

1. **The native project expressly excludes the required new endpoint.** `docs/00-project-brief.md:31` excludes foundation-model pretraining. M5 is a library-based TF-IDF/logistic-regression comparison, not a neural or causal-transformer construction sequence (`learning/curriculum.md:5-14`; `docs/05-ai-and-rag-design.md:56-64`). That prior scope choice is not a prior defect; it now needs a connected mandatory small-model project.
2. **A junior learner enters through infrastructure rather than a useful business baseline.** T001 introduces packaging, a FastAPI health endpoint, pytest and HTTP; T002 adds quality/config/redaction/CI (`docs/09-backlog.md:23-48`; `docs/plans/01-foundation.md:3-15`). The brief's project thesis is concrete, but the first runnable behavior is not yet an AI/business workflow. Add an early synthetic command-line slice and stage intermediate Python responsibilities before requiring framework configuration.
3. **Detailed stack scope risks displacing the learning goal.** PostgreSQL/SQLAlchemy/Alembic, pgvector, LangGraph, UI, queues and tracing are well motivated for the prior production application, but they consume curriculum capacity before a model is built (`docs/02-architecture.md:16`, `:160-162`; `docs/09-backlog.md:174-189`, `:323-338`). Retain actual safety invariants immediately and move substantial infrastructure to bounded optional depth or later demonstrated-need branches.
4. **Retention is suggested, not certified.** The protocol allows `demonstrated` with either no assistance or hints and only prefers a later session (`learning/progress-protocol.md:58-68`). This is an honest modest label under the prior design. It cannot satisfy stronger “independent retained competence” claims without fresh-task identity, observed time, recorded assistance and a separate delayed check. Do not collapse task `done` into route mastery.
5. **No business implementation exists, and scheduling/hardware remain unconfirmed.** The README calls the bundle plans and coaching rather than application code (`README.md:3`; project `AGENTS.md:5`, `:21-29`). The profile says proficiency/schedule/environment are unconfirmed and basic Python is provisional (`learning/learner-profile.md:5-23`). The roadmap makes no duration claim (`docs/08-roadmap.md:3`). Update only explicit user-confirmed constraints, now including five two-hour sessions and CPU-first model training.
6. **Snapshot packaging is not currently internally identical.** The installed skill still references uppercase/underscore files such as `learning/LEARNER_PROFILE.md` and `docs/02_ARCHITECTURE.md`, while the active project uses lowercase/hyphen filenames. The standalone and template also disagree over paths. Offline validation failed the bundle's own identity/init checks. This is an observed snapshot activation blocker; this audit cannot determine whether original packaging or snapshot preparation caused it. Do not blindly run `--sync` against the preserved snapshot.

### Reuse and archive decision

Reuse direct task dependencies, requirement traceability, release-level staging, fake provider/commerce adapters, immutable approval and ambiguous-write cases, observed/learner-reported labels, learning records, optional retrieval and misconception repair, and challenge-set hygiene. Keep the J0–J5 alternative reference-only as C already instructs (`README.md:29`; project `AGENTS.md:9`). Keep a single installed coach for the final repository; package export/template copies should be derived artifacts checked during release, not extra active state owners.

## Required consolidation changes before acceptance

1. **Declare one active objective and authority map.** One learner-facing README, one route, one teaching policy, one current-state snapshot, one factual evidence log, one dependency/task contract, and one tutor. Derived skill exports must have a documented owner and copy check. Preserve previous progress as historical evidence with provenance; do not infer new competence from it.
2. **Use two connected cumulative projects at most.** A support/review application can absorb structured extraction, APIs, RAG, tools, state, approval, evaluation and cost/reliability. A small language-model project should reuse synthetic domain text, artifact/evaluation discipline, and later integrate an explicitly limited local model into a comparison with the application. “Connect” must mean shared meaningful inputs, evaluation or interfaces, not two unrelated courses in one directory.
3. **Add observable Python gates.** Beginning tasks must fit functions/lists/dictionaries. Grow into modules, dataclasses/types, explicit exceptions, file/JSON I/O, iterators/batching, deterministic tests, and maintainable boundaries. Prove intermediate competence through an unfamiliar modification and failure diagnosis; asynchronous I/O can arrive when needed, not as a synonym for proficiency.
4. **Author the missing mathematical/model route.** Require vector/matrix operations and shape reasoning, probability/log likelihood and cross-entropy, finite-difference gradients, manual small-network backprop, training/validation splits and optimization, tokenization with round-trip tests, embeddings/positions, causal attention/mask, residual/block/layer-normalization behavior, and a complete decoder trained from random initialization. The learner writes key operations; a framework can later reproduce them for comparison. Require full runnable train/evaluate/generate commands, saved configuration/checkpoint, declared data/license, validation loss, a baseline comparison, and honest model limits.
5. **Bound compute empirically.** CPU is the canonical required path. Provide a small dataset/context/model configuration and a short smoke training run before expanding it. Measure actual wall time/memory and adjust stage size. GTX 1050 Ti acceleration is optional after environment/capability verification; core completion cannot depend on CUDA, cloud compute, vLLM or quantized adapter-training tooling. An optional SFT/LoRA literacy lab is downstream and cannot replace scratch training.
6. **Fit the stated cadence.** Use 10 hours weekly in five two-hour sessions, keeping setup time distinct and avoiding guaranteed completion dates. A useful recurring rhythm is framing/recall, primitive implementation, failure investigation, integration/evaluation, then fresh transfer plus checkpoint. Session boundaries should create small resumable artifacts rather than require a milestone to fit one session.
7. **Combine helpful scaffolding with honest retention.** Teach a new mechanism before assessing it; use small analogous worked examples when needed; fade help as actual evidence permits. Separate software acceptance, supported practice, independent variation, delayed retention and production evidence. Record task identity, time, assistance and source; a corrected restatement or a passing generated implementation cannot certify mastery. Re-entry after a gap should produce useful output before presenting review administration.
8. **Ship an offline useful baseline with all required commands tested.** B provides the best current starting artifact. Its initial lexical limitation should stay visible until genuinely improved. Add deterministic provider fakes and focused boundary checks without implying provider quality. Do not present A/C validators, health routes, fixture files or planning success as the meaningful application baseline.

## Activation and archive boundary

Activate only the consolidated route, tutor and state after these changes and offline checks. Archive the unused route identities, old skill copies, broad framework catalogues, provider-specific first-call defaults, historical curriculum packs and production-heavy branches as read-only provenance/reference. Keep transferable source fixtures and baseline code in active project directories with a clear owner. Completion evidence, old CI links and generated planning reviews remain historical facts; none establishes new learner progress.

This audit supports component selection and identifies missing acceptance work. It does not certify learner competence, teaching effectiveness, provider behavior, deployment readiness, or the final consolidated implementation, which was outside this read-only snapshot review.
